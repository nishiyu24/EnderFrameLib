# `:core` 高速化・差別化 改善案

現状の構造は [CORE_OVERVIEW.md](CORE_OVERVIEW.md)、現状の数値は `../BENCHMARK.md` を参照。

> **注意**: §1〜§7 の効果見積もりは設計上の推定で、**測定していない**。計測基盤（[MEASUREMENT.md](MEASUREMENT.md)）を整えて
> 実測した結果、**優先度の一部が変わった**。結論は §9 を正とし、§1〜§7 の期待値は §8 の実測と照らして読むこと。
> 着手前に該当段の割合を取り、効果が小さければ打ち切る。
> 「ブラウザを圧倒」できるのは、汎用 Web 互換ではなく **ゲーム内 UI という限定された条件**（小〜中規模の文書、
> 常時 60fps+、同一ドキュメントを長時間再利用、GPU が既にある、サーバー同期あり）に最適化した場合の話。
> Chrome/Blink の全 Web 互換・安全性・JS を同じ土俵で超えるのは目標にしない。

---

## 0. 方針（勝てる軸）

| 軸 | ブラウザの弱み／制約 | 本ライブラリが取れる優位 |
|:---|:---|:---|
| 起動・コールドスタート | 巨大なエンジン初期化 | 数千行のテンプレートを**事前コンパイル済み**で即時表示 |
| 静的に近い UI の定常コスト | 汎用経路を毎回通る | 変化が無ければ**ほぼゼロ**（保持モード＋GPU 駆動のアニメ） |
| 同期 | JS＋DOM 往復 | Headless State の**数 byte 差分**＋型付き束縛 |
| 同じ絵のスケール | 解像度ごとに再ラスタ | SDF/MSDF で**任意倍率が無劣化・ほぼ無コスト** |
| メモリ | 要素あたり数百 B〜KB | SoA/量子化で要素あたり**数十 B** |

優先度は **効果÷リスク** で並べた（§9 のロードマップ）。

## 1. データ指向化（ボトルネックの本丸になりうる）

現状: `DisplayItem`（不変レコード＋`String id`＋`Map events`＋`RenderMeta`）の `List`、`Map<String,String>` のスタイル境界、`LayoutBox`（1.6k 行のポインタ木）。

### 1.1 DisplayList を SoA（Structure of Arrays）＋世代管理にする
- `float[] x,y,w,h` / `int[] color,bg` / `short[] type` / `int[] textRef` … の**列指向バッファ**に変更。`id`/`events`/`meta` は添字でサイドテーブルへ。
- 利点: フレーム毎のアロケーションがほぼ 0、JIT の自動ベクトル化、GPU へ**そのまま memcpy**（§3）。
- 差分化: 要素ごとに `version` を持ち、変わった行だけ書き換える。BENCHMARK が「未達」と認める **DisplayList 生成の差分化**がそのまま解決する。
- 期待: DisplayList 段（showcase 2.6 / large-list 8.0 ms）を 1 桁下げる余地。GC 圧の低下が副次効果。
- リスク: `DisplayItem` を触る全コードが対象（影響大）。移行は「レコード→ビュー（フライウェイト）」のアダプタ経由で段階的に。

### 1.2 スタイルの完全な型付き化（文字列を境界から追放）
- カスケード結果を `String[]` ではなく**プロパティ別の型付きスロット**（`int` 色、`float` 長さ+単位、`byte` enum）へ直接パース。パースは**スタイルシート読み込み時に 1 回**（宣言を事前コンパイル）。
- 実行時 `StyleResolver` は「勝った宣言のインデックスを選ぶだけ」にする（文字列比較・再パース無し）。`var()`/`calc()` を含む宣言のみ遅延評価。
- `StyleSheet` を**ルール配列＋ビットセットのセレクタ索引**（id/class/tag → ルール集合）にし、Bloom フィルタで祖先照合を足切り（Blink/Servo と同系の手法）。
- 期待: Restyle（showcase 9.8 / large-list 19.0 ms。ベンチ中最大の段）の主要因が文字列処理であれば大幅減。**まずプロファイルで確認**。

### 1.3 スタイルの構造共有（Stylo 方式）
- 算出スタイルを継承グループ（Inherited / Reset / Box…）に分け、**同一内容は参照共有**（intern）。500 行のリストなら行スタイルは 1 個に収束し、署名比較（差分レイアウト）も参照比較で済む。
- 現状の `styleShare`（レイアウトごとにクリア）を**永続キャッシュ**へ昇格。

## 2. 「バイトコード化」＝ UI のコンパイル

2 通りあり、**A → B の順**で段階導入できる。

### 2.A テンプレート／スタイルの AOT 事前コンパイル（低リスク・高効果）
- ビルド時（またはリソースロード時の初回）に HTML+CSS を**バイナリ形式（FlatBuffers 風の自前フォーマット）**へ。
  内容: 事前トークン化済み CSS、型付きスタイルスロット（§1.2）、セレクタ索引、DOM 構築命令列。
- 実行時は `HtmlParser`/`CssParser` を通らず**バイナリを mmap して DOM を一括構築**。`ParseLimits` を気にする必要も無くなる。
- 期待: テンプレートを開く時間（初回表示、Headless State の `OpenUi`）がパース分だけ消える。マシン UI を大量に開閉する用途で効く。
- 既存資産: `UiDocumentCompiler` / `CustomTagExpander` がすでにコンパイル段の位置づけ。そこを拡張する。

### 2.B Java バイトコード生成（`java.lang.classfile` / ASM）によるテンプレート特化
- Java 21 では ClassFile API は preview（22+ で標準化）。安定させるなら ASM か `MethodHandle` 合成。
- **バインディング**（`{{key}}`/`data-*`、`Bindings` 1.1k 行の解釈実行）を、テンプレートごとに**専用クラスへ生成**:
  `update(State s)` が「変わったキー → 該当ノードの該当プロパティ」を直コードで書き換える。解釈・ハッシュ引き・ラムダが消える。
- **スタイル適用**も同様に、セレクタ照合を静的に展開した `matches(node)` を生成（定数畳み込み＋JIT のインライン化が効く）。
- **レイアウトの特殊化**: テンプレートが固定構造（スロット格子、ゲージ等）なら、レイアウト式を**定数化した専用 layout メソッド**を生成。動的要素だけ実行時に評価。
- 期待: 「状態 1 キー更新 → 画面反映」の CPU 経路を µs オーダーへ。ただしレイアウト／描画が支配的なら寄与は小さい（§1・§3 が先）。
- リスク: デバッグ性、クラスロード/メタスペース、Minecraft 環境の ClassLoader 事情（NeoForge の module layer）。**2.A が成功してから**。

### 2.C 代替: GraalVM / CDS / AOT キャッシュ
- JDK 側の **AppCDS / Leyden（AOT キャッシュ）** でウォームアップ時間を短縮できる。Mod 環境では適用困難なため、スタンドアロン（`StandaloneViewer`）向けの任意最適化に留める。

## 3. GPU 活用の拡張

現状 GPU は「角丸矩形 SDF・グラデ・影・字形サンプル」を 1 本のシェーダー＋インスタンス描画で処理済みで、**土台は良い**。残りの CPU 依存を減らす。

### 3.1 GPU 駆動のディスプレイリスト（データを毎フレーム詰め直さない）
- `GpuBatchPacker` の `float[256]`/インスタンス（1 KB/図形）を、**永続 SSBO/UBO（または persistent-mapped バッファ）**にして、変わった行だけ `glBufferSubData`。§1.1 の SoA/世代管理と直結。
- GL 4.3+ があれば **`glMultiDrawArraysIndirect` / compute** で、カリング・クリップ判定・ソートを GPU 内で行い、CPU→GPU は差分のみにする。GL 3.2 core（現状）との二段構え（機能検出で切替）。
- 現状の 1 バッチ 512 件・1 KB/件は、数千要素 UI でバス帯域と CPU 側パックが効く。圧縮（§4）と併用。

### 3.2 アニメーション／変形を GPU で解く
- `transition`/`@keyframes` の補間（現状 `CssAnimator`＋`PaintSceneDriver` が CPU で毎フレーム解決）を、**開始値・終了値・イージング・開始時刻**をデータに積み、頂点/フラグメントシェーダーが `time` から補間。CPU は**アニメの開始/終了イベントだけ**扱う。
- 効果: アニメ中の要素が増えても CPU コストが定数。ホバー/トランジション主体の UI で顕著。
- 制約: 変形がレイアウトに影響しない `transform`/`opacity`/色に限る（それらは既に「再レイアウト不要」扱い）。

### 3.3 文字描画: ビットマップ → SDF / MSDF
- 現状: FreeType でグリフをラスタ→`AtlasPacker`→サンプル。`scale` アニメ時に量子化しても約 90 種が VRAM に乱立。
- **MSDF アトラス**（フォント 1 書体 1 回生成）にすれば、**任意倍率・回転・アニメが同一テクスチャ**で成立し、アトラス再生成と VRAM 乱立が消える。小サイズの可読性は**ヒンティング付きビットマップとのハイブリッド**（小サイズ＝ビットマップ、拡大・回転時のみ MSDF）で補う。
- 回転文字が CPU 層に落ちる現状の制約（`LwjglGlRenderBackend` Javadoc）も消える。
- 生成: 事前（ビルド時）に CJK を含む場合はサイズが爆発するので、**必要文字だけ遅延生成＋LRU**（現在の `AtlasCache` の枠組みを流用）。

### 3.4 フィルタ・影・ぼかしの GPU 化
- `FilterOp`/`backdrop-filter`/`mix-blend-mode` の CPU 層経路（`LayerFx`）を、**ダウンサンプル→分離ガウス（もしくはデュアルKawase）→合成**の GPU パスへ。現状もグループ用 FBO（`LayerPool`）はあるため、パスを足す形。
- 影は既に SDF＋erfc 近似で解析的なので維持。

### 3.5 タイル／ダメージ追跡の GPU 側
> **ゲーム内の実測で優先度が上がった**（§8）。静止していてもコア経路が毎フレーム描き直しているため、まず**面単位の再描画スキップ**
> （変化もアニメも無ければ前のテクスチャを貼るだけ）を入れる＝§9 項目 2。タイル単位のダメージ追跡はその次の段階。

- 画面を 64×64 等のタイルに分け、**ダメージのあったタイルだけ再描画**し、静止タイルは前フレームのテクスチャをキャッシュ（ゲーム UI は大半が静止）。ソフト側 `dirtyBounds` の考えを GPU に拡張。
- Minecraft 統合側では、UI を**テクスチャに焼いて 3D 面（ブロック面・手持ち）に貼る**既存構造と相性が良い。更新頻度を下げる（例: 静止時は 0 回、アニメ時のみ 60Hz）。

### 3.6 描画 API の抽象を活かす
- `GpuBatchPacker` は API 非依存（Vulkan SSBO への言及あり）。将来 Vulkan/WebGPU バックエンドを足す場合、`BatchDevice` に実装を足すだけの構造を維持する。**今すぐ Vulkan 化する価値は低い**（GL で CPU 側がボトルネックの間は効かない）。

## 4. 量子化・圧縮

### 4.1 GPU 転送データの量子化（帯域・VRAM）
- 1 インスタンス 64 テクセル × float4 = 1 KB を、**矩形＝`short`/`half`（1/64px 単位の固定小数、LayoutUnit と同じ精度）**、色＝RGBA8、姿勢＝half、角丸＝`byte` 比率…へパック。1 図形 **100〜200 B 程度（5〜10 倍減）**を狙える。
- シェーダー側は `unpackHalf2x16` / `unpackUnorm4x8`（GLSL 150 で可）。差分更新（§3.1）と合わせて CPU→GPU 転送が支配項でなくなる。
- 精度: 座標は 1/64px、色は 8bit 相当で十分（既に画素単位の SDF 式）。**CPU/GPU 画素一致**テストがあるので、許容誤差の再定義が必要（ゴールデン更新）。

### 4.2 レイアウトの固定小数化
- 現状 `float`。Chrome は 1/64px の `LayoutUnit`（`TextShaper.WRAP_TOLERANCE` もその対応）。**整数演算にすれば再現性が上がり、署名比較（差分レイアウト）が厳密一致**でき、ブラウザとの忠実度の誤差源（`FIDELITY.md`）も減る。速度面の利得は小さいので「正確さと決定性のため」と位置づける。

### 4.3 ネットワーク／ディスクの量子化
- Headless State は既に番号化済み（20 bytes/更新）。さらに **`double progress` → 量子化 `short`（0..65535 / 範囲辞書）**を値型として宣言できるようにし、更新を 10 bytes 未満へ。テンプレート側で `data-range` と `data-quant="u16"` 等を宣言。
- 画像／アトラスは **BC7/ASTC などのブロック圧縮**（VRAM 1/4〜1/8）。GPU 側で対応拡張を検出して使う（要エンコード時間の考慮 → 事前ビルド向き）。
- 字形アトラスは 8bit 単色（R8）で既に小さい。MSDF は RGB8。

### 4.4 文字列のインターン化
- クラス名・タグ名・プロパティ名・id を**整数 ID**にし、`HtmlElement` の属性/クラス照合をハッシュ引きなしのビット/整数比較へ。§1.2 のセレクタ索引と合わせて効果。

## 5. 並列化

現状パイプラインはシングルスレッド。UI は小規模なので**細粒度並列はオーバーヘッド負け**になりやすく、**粒度を選ぶ**。

| 並列化の粒度 | 内容 | 期待 | リスク |
|:---|:---|:---|:---|
| **パイプライン分割（推奨）** | 「前フレームの描画」と「次フレームの Restyle/Layout」を別スレッドで重ねる（ダブルバッファの DisplayList） | フレーム時間 ≈ max(段) に | 世代管理・DOM 変更のスレッド境界 |
| **独立サブツリー** | `contain: layout size` や `overflow` 確定のスクロール領域を `ForkJoin` で並列 measure（`RelayoutBoundaryTest` の境界が既にある） | large-list のような多数行で有効 | 小文書では逆効果。閾値で切替 |
| **テキスト整形の先行計算** | `TextShaper` の結果を非同期にウォームアップ（フォント読込・グリフ生成） | 初回表示のカクつき除去 | キャッシュのスレッド安全性（`synchronized` 22 ファイルあり） |
| **画像デコード・グリフ生成** | 既にワーカあり。GPU アップロードのみメインへ | — | — |

Java 21 なので **仮想スレッド**は I/O 系（HTTP・動画）で使えるが、CPU バウンドの描画準備には効かない。

## 6. CPU ラスタの SIMD / 低レベル最適化

- `SoftwareRenderBackend` は基準画像・CI・サーバー用途の主役なので、そこだけ **`jdk.incubator.vector`（Vector API）**で塗り・合成（プリマルチプライド ARGB のブレンド、ガウス、グラデ）をベクトル化。Java 21 ではインキュベータで、`--add-modules` が必要＝**Minecraft 本体側では使えない可能性**が高い。スタンドアロン専用の高速パスに限定。
- `Rasterizer`（4 サブスキャンライン）は**符号付き面積累積（font-rs / Pathfinder 方式）**にすると、サブサンプル数に依存せず正確な被覆率を 1 パスで得られる。
- `Pixmap` を `int[]` から `MemorySegment`（Java 21 preview / 22 標準）や direct buffer にすると、GL 転送・PNG 出力がコピーなしになる。

## 7. 新規の差別化機能

1. **完全なアイドルゼロコスト**: 変化が無いフレームは Restyle/Layout/DisplayList/GPU 送信を全て飛ばし、前フレームのテクスチャを再利用。**実測で 3 µs/フレームと既に達成済み**（§8）。要素数を増やしても保たれることは `IdleCostScalingTest` で守る（維持項目）。
2. **フレーム予算スケジューラ**: 1 フレームあたりの UI 予算（例 0.5 ms）を設定し、超えそうな更新は次フレームへ分割（レイアウトの段階的実行、リサイズの現行 `RESIZE_THROTTLE_FACTOR` を一般化）。
3. **決定論的レンダリング**: CPU/GPU 画素一致を既に目指している。固定小数（§4.2）で**プラットフォーム間のビット一致**まで行けば、サーバー側で UI のスナップショット検証（アクセシビリティ・自動テスト・リプレイ）が可能。これは一般的なブラウザに無い性質。
4. **サーバー同期とレンダリングの共設計**: 状態差分から「どの要素が汚れるか」を**テンプレートのコンパイル時に静的解析**（キー→ノード/プロパティの依存グラフ）。実行時は依存グラフを辿るだけで Restyle の探索が不要（§2.B と連動）。
5. **LOD／視錐台カリング**: ブロック面・手持ち UI は画面上で小さい／遠いことが多い。見かけの大きさに応じて**解像度・フィルタ品質・更新頻度**を落とす。

## 8. 計測の整備（2026-11-07 実施済み）

[MEASUREMENT.md](MEASUREMENT.md) に手順と実測。道具は次の 5 つ。

| 当初の不足 | 結果 |
|:---|:---|
| 段ごとの内訳プロファイル | `StageProfiler` / `PipelineStage` を `core/diag` に追加し、`RenderPipeline`・`DisplayListBuilder` に差し込み（無効時は volatile 読み 1 回）。`:core:profile` で表にする。JFR も同じタスクで取れる |
| JMH によるマイクロベンチ | `core/src/jmh`（`PipelineBench` / `PaintBench`）。`:core:jmh`。`-prof gc` で割り当て量も出る |
| GPU の `GL_TIME_ELAPSED` | `LwjglGlRenderBackend.enableGpuTiming()`（4 本の輪で非ブロッキング）。実 GL で動作確認済み |
| ゲーム内のフレーム時間 | **実施済み**。`SurfaceRenderer` / `CoreGpuSurface` に差し込み、`/enderframe_profile` で取る（MEASUREMENT.md §2・§4.4）。静止状態のみ。動いている UI・HUD・ブロック面は未計測 |
| ブラウザ比較の土俵 | **未実施**（参考値としての手順整備のみ） |

### 実測で分かったこと（ソフトウェア描画・開発機。詳細は MEASUREMENT.md §4）

| 想定（§1〜§7 の前提） | 実測 |
|:---|:---|
| Restyle が最大の段 | 冷たい再スタイルは 1.5〜4.3 ms だが、実フレームでは差分化済み（`style+build` 0.3 ms）。**定常では支配項でない** |
| DisplayList 生成が重い | 0.5〜2.1 ms（JMH）で時間は小さい。ただし**割り当てが大きい**（large-list 5.2 MB/op）。局所更新の実フレームでは 0.2 ms |
| アイドル時のコスト | **3 µs/フレーム**。既に達成（§7.1 は新規機能ではなく維持項目） |
| （想定外）CPU ラスタが支配的 | `paint(cpu)` が showcase の全再描画で 43.8 ms、large-list の局所更新でもフレームの約 80%（3.3〜3.5 ms）。1 フレーム約 9 MB を割り当て |
| 再レイアウトの内訳 | `measure` が 7.9 ms（showcase）で最大。`place` は 0.1 ms |

### ゲーム内の実測（2026-11-07・1600×900・静止した showcase。詳細は MEASUREMENT.md §4.4）

| 経路 | surface（CPU 側）ms/フレーム | GPU ms/フレーム |
|:---|:---:|:---:|
| 従来（`useCoreBackend=false`） | 2.49 | 計測不可 |
| コア（`useCoreBackend=true`） | 0.84（`core-render` 0.76 / `core-blit` 0.04） | 1.68 |

| 想定 | ゲーム内の実測 |
|:---|:---|

**方針の変更点**: 当初は「Restyle・DisplayList の構造改革 → GPU」を推していたが、スタンドアロンの実測では (a) 定常の再スタイルは既に軽い、
(b) アイドルは既に 3 µs、(c) 時間・割り当てとも**ラスタ側と measure**が大きい、と出た。さらにゲーム内の実測（項目 1）で、
(d) 本番のコア経路は GPU 描画なので**支配項は CPU ラスタではなく GPU 側**、(e) **静止していても毎フレーム描き直している**、と分かった。
そこで順序を改め、**まず静止時の再描画スキップ（項目 2）**を入れて静止時のコストを 0 に近づけ、次に動いている UI を測り（項目 3）、
それでも GPU が支配的なら転送の量子化（項目 4）へ進む。CPU ラスタの割り当て削減（項目 5）と measure の削減（項目 6）は
スタンドアロン/サーバー描画と「文書を開く瞬間」には効くが、ゲーム内の定常フレームには効かないので後ろに回した。
構造改革（SoA・型付きスタイル）は正しさのテスト網（差分ファジング・忠実度 138 ケース）があるので安全に進められるが、効果が見えるまで保留する。
