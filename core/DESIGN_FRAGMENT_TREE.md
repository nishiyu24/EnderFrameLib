## 0. 要約

- C1（表示リストを部分木の記憶の連結で作る）を **平らな配列の連結**で実装すると、large-2000 のように 1 つの親の下に 2,000 の子が並ぶ文書で、1 か所の変更でも兄弟の数だけ走査が要り、`hover`・`style` のフレームが 3〜4 倍になる（§6-140）。パッチが速いのは、変わった箱の範囲だけを触るから。
- よって「断片」を **木**（兄弟の並びは不変のブロック配列。足りなければ平衡木。§0.5 M7）で持ち、変わった葉から根までの変わった部分だけを組み直す。連結結果は消費者（`PaintSceneDriver`・GPU・ヒットテスト）が読む。
- 消費者の改修（C2）を同じ設計に含める理由: 断片が同じ実体なら、索引・再生・損傷範囲も **区間ごと**に再利用できる。生成側だけ木にして消費側が全項目を走査すると、利得が消える。
- **保守性を最優先**（§0.5 の原則 M1〜M8・§0.6 のスコープ縮小）。消費側の改修（F4・F5）は条件つき。
- 段階は F0〜F5。**F0（配線しない試作）で時間の合否線に届かなければ C1・C2 を見送る**（§8）。

## 0.5 保守性の設計原則（速さより先に決める。2026-11-21 追記）

過去の不具合（§6 の約 15 件）の出どころは 4 つ: ①手書きの「退く条件」の漏れ ②範囲・添字の数え違い ③出力のその場書き換え（エイリアス） ④ビルダーが持つ暗黙の可変状態（`currentRoot`・`windowedBuild`・`activeMovingEpoch`・`fragIds` など）が鍵に入っていないこと。新設計は、これらを**書き方で不可能にする**。さらに、新しい構造が新しい不具合源にならないよう、次の 8 原則を設計の拘束条件にする。

| # | 原則 | 具体 | 機械的な固定 |
| :-- | :-- | :-- | :-- |
| M1 | **純粋な組み立て**: `build(box, ctx)` は引数と箱の木だけを読む。ビルダーの可変欄（`currentRoot`・`windowedBuild`・`parentRelative`・`activeMovingEpoch`・`fragIds` など）を読まない | 現在ビルダー欄で受け渡している文脈は、すべて 1 つの不変レコード `PaintContext` に集め、`build` の引数にする。鍵は `PaintContext` の全欄＋箱の版から**機械的に**作る（鍵の項目を手で並べない） | `FragmentBuilder` に可変インスタンス欄が無いこと（`ClassShapeRatchetTest` 流のリフレクション検査）。`PaintContext` に欄を足すと鍵に自動で入る |
| M2 | **出力は不変・生成後に触れない** | `Fragment`・縄は `final` 欄のみ。項目の可変部分は B9 の `PaintCell` だけ（既存の契約）。断片を受け取った側が書き換える口を作らない | 型検査（欄が全て `final`・配列を外へ出さない）＋ `ItemDiffRatchetTest` 流の「`Fragment` を書き換える呼び出し 0」 |
| M3 | **位置を数えない**: 表示リストの添字・`dl*`・描画順の通し番号を、生成側に持ち込まない | 順序は「子リストの順＋層」だけで決まり、添字は消費者が接頭和から**読む**。`LayoutBox` に書き戻す欄は作らない | `SliceWriteSiteRatchetTest`（上限 0）・`FragmentBuilder` が `int` の位置を引数に取らないこと |
| M4 | **増分専用のコードを持たない**: 全面＝記憶が空の増分。「挿入位置の探索」「後続のずらし」「祖先の寸法合わせ」は書かない | 子の増減は子リストの差し替えだけ（縄の分割・連結）。並びは再計算ではなく構造が保つ | `PatchSiteRatchetTest`（スイッチ・`cant`・パッチ専用クラスの行数が下がる一方） |
| M5 | **記憶の鍵は小さな 1 か所**: 鍵の比較・生成は `FragmentKey` の 1 クラスだけ。記憶を引く呼び出しは `FragmentMemo.get` の 1 か所 | 当たり・外れのカウンタと、検証モード（§6）の差し込みも 1 か所に集約 | 記憶テーブルへの他からのアクセス禁止（`FragmentMemo` 以外で `Map<LayoutBox, Fragment>` 型を持たない） |
| M6 | **まず影（shadow）で動かす**: 新しい断片経路は、旧経路が正の出力を作る間、**同じフレームを併走して毎回比べるだけ**にする（本体の出力に影響しない）。差分ファズ・実文書・テストが全て 0 件ずれになってから切り替える | F1 は影モード。切り替えは 1 つのスイッチを反転するだけで、戻せる | 影モードの不一致は `:core:test` で失敗にする。切り替え後も旧経路を 1 段（次の段の完了まで）スイッチで残し、最後に消す |
| M7 | **最小の構造から始める**: 縄は「平衡木」ではなく、まず**ブロックの配列（2 段の連結リスト）**で足りるかを F0 で測る | 項目 462・箱 2,006 の large-2000 なら、葉 32 要素の 2 段（約 15 ブロック）で更新 O(ブロック数) が `0.02 ms` に収まる見込み。平衡木（B 木）は**測って足りないときだけ**入れる | F0 の表に「2 段」「B 木」の両方の時間を載せ、複雑な方を選ぶ理由が数字で残ること |
| M8 | **部品の大きさと責務を縛る**: 新しい型は 1 つ 1 責務・1 クラス 400 行以下。`DisplayListBuilder` に足さない（これ以上太らせない） | `Seq`（並び）・`Fragment`・`FragmentKey`・`PaintContext`・`FragmentMemo`・`FragmentBuilder`・`FragmentList`・`FragmentVerifier` の 8 型に分ける | `FileSizeRatchetTest`（新クラスの上限 400 行）。`DisplayListBuilder` の行数の上限は増やさず、F2 以降は下げる |

加えて、**検証は 3 層**にする:

1. **型・単体**: 縄は `ArrayList` を参照実装にした**ランダム操作の性質テスト**（挿入・削除・連結・分割・取得。種を多数）。壊れた縄を単体で捕まえ、箱の木に持ち込まない。
2. **差分**: 断片経路 vs 記憶無効の全面（既存の `MEMO_ENABLED=false`）。`IncrementalVsFullTest`・差分ファズ種 1〜1500・実文書ゴールデン。
3. **鍵の漏れ**: `VERIFY_FRAGMENT`（当たったとき作り直して比べる）に加え、**鍵の要素を 1 つずつ外すミューテーション**を CI の 1 テストにして「外すと赤になる」ことを毎回確かめる（記憶の `fuzz-triage` の revert-each-fix と同じ発想。外しても赤にならない要素は、鍵が冗長か検証が弱い印）。

### 0.6 保守性のためのスコープの縮小

- **C2（消費側）は条件つきに格下げする**。F1〜F3 は `FragmentList`（平らな `List` として読める）で消費者を**変えない**。`PaintSceneDriver` の索引更新は、large-2000 で項目 462 の走査 `0.001 ms` 級で、現状で支配的でない（§6-139・140）。F4・F5 は「F3 後の計測で消費側が合否線を超えているとき」だけ行う。同時に作り替える量が減り、不具合の混入点が減る。
- **~~`escapees` を `memoizable=false` に倒す~~（F0 で撤回）**: 実文書の調査で、不可分なインライン（flex/grid アイテム・inline-block）が箱の 45〜68% を占め、記憶しない扱いにすると大半が記憶できなくなると分かった。代わりに、**付録 E の全分類を「箱が親へ渡す層別の列」として一般化**した（§3.4・§11）。float・不可分なインライン・位置指定・スタッキングコンテキスト・スクロールバーはすべて断片の種類（`Kind`）として扱い、特別扱い（`memoizable=false`）は持たない。
- **絶対座標モード（U3）は対象外**（`memoizable=false` の一種）。親相対モードだけを高速化し、絶対モードは全面と同じ経路にする。

### 1.2 消費側（C2 の対象）が項目の何に依存しているか

| 消費者 | 依存 | 断片の木で必要なもの |
| :-- | :-- | :-- |
| `PaintSceneDriver.prepare` | 平らな `List<DisplayItem>`、添字、`parentIdx[]`、`itemVersion[]`、`indexedById`。前回との差を `patchIndexByDiff/Shift/Move` の 3 経路で取る | 項目の**同一性**（`==`）と **鍵**（`key()`）。断片の同一性があれば区間ごと「変化なし」 |
| `ItemDiff.unchanged(prev, cur, seenEpoch)` | `prev == cur && cur.paintEpoch() <= seenEpoch`（B9: 塗り・移動量は `PaintCell` へ書いて項目を作り直さない） | 断片を再利用するとき項目の実体を**同じまま**返すこと。区間の「最大 `paintEpoch`」を断片が持てば区間ごとに判定できる |
| `Painter.tryPatchItems(items, indices, n)`（GL/CPU の差分描画）・`GPU_DAMAGE`・`DamagePlanner` | 変わった添字の列 | 変わった断片の範囲＝添字の区間（接頭和から求める） |

| `HitTestIndex.patch(changed)` | 変更した節の数に比例 | 変わらない |

## 3. 設計

### 3.1 断片（`Fragment`）

箱 1 つの**描画の出力**を表す不変の値。

```text
Fragment {
  key        : FragmentKey                 // 記憶の鍵（§3.2）
  layers     : Seq<DisplayItem>[4]         // block / float / inline / （自分の背景など自身の項目は block に含む）
  escapees   : List<Escapee>               // 外のスタッキングコンテキストへ出ていく位置指定・z-index 付きの子孫（§3.4）
  count      : int                         // 自身の全項目数（layers の合計。escapees は含まない）
  maxPaintEpoch : int                      // 区間の変化判定（§4.2）
}
Seq<T> = 不変の並び。F0 は 2 段（ブロック 32 項目の配列の配列）で始め、足りなければ平衡木（M7）。ブロックは ImmutableItemList と同じ大きさ
```

- `layers` が 4 つに分かれるのは、CSS 付録 E の描画順（ブロック背景 → float → インライン → 位置指定）が「層ごとに、親の兄弟全体にまたがって先に・後に」並ぶため。子の断片を連結するときは**層ごとに**連結する（現行の `Chunk.{blockItems, inlineItems}`・`BoxSlice` と同じ区分）。
- 子の並び（`children`）の連結は、各層で `concat(childSeq_0, …, childSeq_n)`。**並びが不変の構造なので 1 つの子の差し替えは、変わったブロックだけの作り直し**（2 段なら O(ブロック数)、平衡木なら O(log n)）。これが 2,000 兄弟での O(兄弟数) の項目走査を避ける要（M7: 2 段で足りるかを先に測る）。
- 窓付き表示（`WINDOWED`）: 窓の外の箱は **空の断片**（`culled` 印付き）を返す。窓の出入りで変わるのはその箱の鍵（窓判定の結果）だけなので、窓の移動は「出入りした箱の断片の差し替え」になる。現行の `culledBoxes` の管理と `windowIntact` は消える。

### 3.2 鍵（`FragmentKey`）— 「実際に読んだもの」

箱の出力を決める入力を**明示のレコード**にする（計画 §3.3 約束 3・C3 と同じ線引き）。

| 鍵の要素 | 内容 |
| :-- | :-- |
| 描画入力の版 | `paintStamp`（箱自身のスタイル・文字・属性・幾何）。既存の `BoxMemo` の鍵と同じ |
| 部分木の版 | 子孫のいずれかが変わると上へ伝わる版（`pathPaintStamp` に相当）。**子の断片の同一性の列**で代替できる（子が全て同じ実体なら、部分木は同じ） |
| 文脈 | クリップの鎖（`ClipRect` の正規化 id）・スクロールの節 id・属するスタッキングコンテキストの z 文脈・親相対の原点 `(ox, oy)`（`parentRelative` モードのとき）・窓の判定結果・`devicePixelRatio` |
| 世代の外部入力 | 書体・画像・`SHAPE_EPOCH`・`MEASUREMENT_EPOCH`（C3 の鍵のレコードと共有） |

- **親相対の原点を鍵に入れる**ことで、平行移動した部分木（現行の `translated` 経路）は鍵が変わる。ここは `parentRelative` モードで項目の座標が親原点からの相対のため、原点が同じなら断片が同じになる（現行モードの既定。絶対座標モードは F1 で対象外として分け、後述 §7 U3）。
- 鍵の比較は `equals` ではなく**フィールドごとの `==`**（確保を避ける。`BoxMemo.match` と同じ）。

### 3.3 組み立て（全面と増分が同じ関数）

```text
Fragment build(box, ctx):
  key = keyOf(box, ctx)
  if memo[box] != null and memo[box].key matches key: return memo[box]        // ← 当たれば子へ降りない
  childFrags = for each child c (in paint-phase order): build(c, ctxFor(c))
  frag = assemble(self(box), childFrags)    // 自身の項目＋層ごとの縄の連結＋escapees の合流
  memo[box] = frag
  return frag
```

- 「当たれば子へ降りない」のため、鍵に **部分木の版**が要る（箱自身の `paintStamp` だけでは子孫の変更を見落とす）。部分木の版は変更時に祖先へ伝える（`paintStamp` の更新が既に祖先の `pathPaintStamp` を無効にしている。その仕組みを再利用する）。
- 全面＝`memo` が空のとき。増分＝`memo` が当たる部分木を飛ばす。**同じ `build`** で、増分だけのコード（挿入位置の探索・後続のずらし・範囲の振り直し）は存在しない。
- 子の増減は、`children` の縄の差し替え（挿入・削除は縄の分割と連結。O(log n)）。**挿入位置は「子リストの添字」で決まり、表示リストの添字を数えない**ので、現行の挿入位置・描画順の数え違い（§6-80・81・108・109・112・113・119）は構造上起きない。

### 3.4 スタッキングコンテキストと層の受け渡し（F0 で確定した一般形）

> **F0 の結論**: `escapees` という別の仕組みは要らない。箱は親へ **7 つの層の列**（blocks / floats / inlines / 負の z / 位置指定 / 正の z / after）を渡し、親は子の列を子の順に並べた永続ベクタで持つ。箱の種類（ブロック・インライン・float・不可分・位置指定・スタッキング）が、自分の出力をどの層へ入れ、子の層をどれだけ消費するかを決めるだけ（`PaintOrder.classifyPlain` の写し）。スタッキングコンテキストの根と疑似コンテキスト（float・不可分・位置指定）が中身を 1 本にまとめて（`emit`）親の 1 つの層へ入れる。以下は初稿の記述（`escapees`）で、意味は上の一般形に置き換わる。

- 位置指定・`z-index` 付きの子孫は、親の断片の層には入らず、属する**スタッキングコンテキストの根**の断片へ `escapees` として渡る。根では z と文書順で安定整列して合流する（現行の `PaintNode` / `PaintLayers` の整列に相当）。
- 根の断片の `layers` は、合流後の縄。合流は「escapees の数ぶん」の縄の連結で、通常の文書で escapees は少ない。多い文書（位置指定が数千）は合流が O(escapees) になる。それは現行（`StackingSubtreePatch` が部分木全体を組み直す）以下。
- フィルタ・マスク・ブレンドなどの層（`LayerSpec` の `span`）は、根の断片が自分の全項目数を持つので `span = frag.count`（O(1)）。**層の `span` の数え違い**（§6-109 型）が消える。

### 3.5 連結結果の見せ方（消費者への口）

`FragmentList`（`List<DisplayItem>` を実装し `RandomAccess` ）を、根の断片の `layers` を連結した縄の上に載せる。

- `get(i)` は O(log 項目数)（縄の降下）。走査（`iterator`）は O(項目数)。
- 既存の消費者（`PaintSceneDriver` ほか）は**そのまま**読める（F1〜F3 の間はこれで足りる。C2 の F4 で区間単位に拡張）。
- `ImmutableItemList` の 32 要素ブロックは、縄の葉と同じ大きさ。葉を共有すれば、`ImmutableItemList.from(prev, src)` のコピー（同じ長さのとき）が不要になる（F3 で統合する）。

## 4. 消費側（C2）

### 4.1 索引（`PaintSceneDriver`）

- 項目ごとの `parentIdx[]` ・`itemVersion[]` ・`indexedById` は**添字**に依存する。断片の木では、断片ごとに**局所の添字**で持ち、全体の添字は接頭和（縄の size）で求める。
- 変化の取り方: 断片が前回と**同じ実体**で `maxPaintEpoch ≤ seenEpoch` なら、その区間は「変化なし」で飛ばす。変わった断片だけ項目を比べる（現行 `patchIndexByDiff` の全項目走査を、断片単位へ）。
- 3 つのパッチ（`ByDiff`・`ByShift`・`ByMove`）は、**1 つの照合**になる: 「前回の断片列」と「今回の断片列」を断片の同一性で突き合わせ、新しい断片・消えた断片・動いた断片（接頭和が変わった断片）だけを索引へ入れる。並びの入れ替え（Move）・挿入・削除（Shift）は断片列の差として同じ扱い。

### 4.2 再生・損傷範囲

- 項目の再生（`GL_REPLAY`・`SOFT_GL_REPLAY`）の安全条件（§6-27 の補間値・クリップ slot・CPU 層の順序）は、**断片の鍵**に明示する（「再生してよい」＝断片が同じ実体で、鍵の文脈が同じ）。暗黙の条件が検証モードで見える。
- 損傷範囲（`GPU_DAMAGE`・`SOFT_DAMAGE`・`DamagePlanner`）は「変わった断片の外接矩形の和」から出す。断片が自分の外接矩形（子孫を含む）を持てば、O(変わった断片数) で出る。

### 4.3 B9 との整合

- 塗り・移動量の変化は `PaintCell` に書いて項目を作り直さない（B9）。断片は**項目の実体を保つ**ので、この書き込みは断片の同一性を変えない。区間の `maxPaintEpoch` は書き込みのたびに根へ伝える必要がある（`ChunkClock` が既にブロックごとに持つ時計の、断片版）。
- `patchSortedSlices` の「塗りだけが違うなら項目を作り直さず前の項目のセルへ書く」（`sameExceptPaint` → `repaintFrom`）は、**断片の組み立ての中の葉の再利用**として残す（項目単位の再利用であって、パッチではない）。

## 9. 見送ったほうがよい選択肢（検討の記録）

| 案 | 見送り理由 |

| 平らな配列の連結（C1 を単純に実装） | §6-140 のとおり、2,000 兄弟で 1 か所の変更でも O(兄弟数)。時間 KPI を守れない |

## 13. F1b: 構造共有・変更の伝播・パッチ後の影（2026-11-21。**計測部分は完了、葉の作り方は未着手**）

F1b（§12.2）の 3 項目のうち、「葉の作り方」以外を先に進めた。結果は次のとおり。

### 13.1 構造共有（断片が前フレームと同じ実体になるか）

`Fragment.build` に「前回の断片と中身（種類・z・自分の項目・子の断片）が項目の実体まで同じなら、新しく作らず前回の断片を返す」を足した（影モードが前回の木を持つ。`FragmentVerifier.State`）。`FragmentReuseTest`:

| 状況（合成文書 300 行・断片 615 節） | 新しく作った節 | 再利用した節 |
| :-- | --: | --: |
| 何も変えずに全面で描き直す | **0** | 615 |
| 1 つの箱のクラスを変えてから全面で描き直す | **4**（変えた箱から根までの道） | 611 |

→ 箱ごとの記憶（`BoxMemo`）が項目の実体を保つので、**断片は前フレームと同じ実体になる**。C2 が「断片の同一性で区間ごとの変化なし」を言う前提（§4.1）が成り立つ。

### 13.2 変更の上向き伝播を含めた時間（U9 の判定）

`FragmentBenchTest` の「伝播あり」: 変わった箱から親をたどって根までの道を求め、各階層で兄弟の中の位置を線形に引き（`Fragment.kids` の箱の同一性）、更新し、平らな列へ展開する。

| 文書 | 兄弟数 | 伝播あり mean / p50（更新＋展開込み） | 伝播なし（F0） |
| :-- | --: | --: | --: |
| 40 行 | 40 | `0.0020` / `0.0019 ms` | `0.0020 ms` |
| 500 行 | 500 | `0.0021` / `0.0019 ms` | `0.0020 ms` |
| 2,000 行 | 2,000 | **`0.0026` / `0.0024 ms`** | `0.0027 ms` |

→ 兄弟 2,000 の線形の引き（≒ 1,000 回の同一性比較）は **1 µs 未満**で、F0 の値にほぼ上乗せされない。**U9 は解決**（箱に添字を持たせず、親の断片の子の列を引く形でよい）。残る費用は葉の作り方（現行のパッチでは large-2000 `hover` の display-list 全体が `0.001 ms`）で、合計の見積もりは `0.005 ms` 未満。合否線 `0.02 ms` に収まる見込み。

### 13.3 パッチ後の表示リストを影で比べる試み（**撤回・知見**）

`patchBoxes`・`patchChildSlices` の後にも断片の木と比べると、**3 テストで食い違った**: `FloatContainmentMemoTest`（断片 2 件少ない）・`LocalUpdateTest$ChunkRetention`・`ParallelMutationStressTest`（件数は同じで並びが違う）。ほかに確保量を測る 2 テストは、検証自体の確保で落ちた（検証モードの副作用）。

- 表示リスト自体は正しい（`IncrementalVsFullTest` などが全面と一致を確認している）。食い違ったのは、**パッチ後の `dl*`（箱ごとの範囲・描画順の記録）が実際の並びと一致しない**状態。つまり旧経路のパッチは、見える出力を正しく保ちながら、内部の範囲の記録を厳密には保っていない。
- これは C1 が消そうとしている「範囲・添字の数え違い」（M3）の実例で、断片の木（位置を数えない）の動機を補強する。同時に、`dl*` に頼る影ではパッチ後を検証できない。**パッチ後の検証は、断片が自分で項目を作る（F1b の残り）か F2 で置き換えるときに、独立した比較として行う**（今は撤回し、全面の描画の後だけ）。
- 既知の不具合としては扱わない（出力の食い違いは観測されていない）。パッチ後の `dl*` が次のパッチの入力になる経路で、まれに誤る可能性は残る（差分ファズでは見つかっていない）。

### 13.4 F1b の残り（葉の作り方）

1. 断片の葉を、旧経路の出力の切り出しではなく、箱ごとの描画（`drawBoxSelfMemo`・`BoxMemo`）から作る。文脈（クリップ・親 id・親相対の原点・窓・動く祖先）を不変の `PaintContext` にまとめ、鍵にする（M1・M5）。
2. 断片の記憶（`FragmentMemo`）。鍵の一致で子へ降りない（今の構造共有は葉を作ってから比べるので O(箱数)）。
3. 影モードをパッチ後にも広げる（上の 2 を済ませたあと）。

→ ここから先は旧経路のコード（`DisplayListBuilder` の描画・`BoxMemo`・`PaintOrder` の文脈）を断片の組み立てから呼べる形に切り出す必要があり、設計の判断が要る（§13.5）。

### 13.5 判断が要る点（葉の作り方）

| 論点 | 案 A: 旧経路の描画を断片から呼ぶ | 案 B: 断片が全面の経路そのものになる（F2 へ前倒し） |

## 14. B 案: 断片の経路が全面の描画そのものになる（2026-11-21。**スイッチ付きで完了・既定は旧経路**）

§13.5 の案 B を採った。旧経路（`PaintOrder.paintTasks` で分類 → 平らなタスク列 → `executeTasks` で順に描く）の代わりに、`FragmentPaint` が箱を再帰して、その場で箱の項目を描き、種類（`Fragment.Kind`）ごとに層へ組み立てる。`Shortcut.FRAGMENT_BUILD`（`-Denderframe.paint.fragments=true`）で切り替え、断片で表せない描画（仮想化・Top Layer・マスク・文書の根でない起点）は旧経路へ落ちる。

### 14.1 旧経路と共有した部分（重複を作らない）

- `PaintOrder.beginPass()`（`paintTasks` の前処理）と `PaintOrder.enterChildren()`（中身に掛けるクリップ・子の親 id・スクロールの節の登録）・`wantsScrollbars()`。旧経路の `collectChildren` もこれらを呼ぶ。
- 箱の項目は旧経路と同じ `order.executeTask → painter.draw → drawBoxSelfMemo`（箱ごとの記憶つき）。レイヤーの錨は `FragSeq.Layered` が展開時に `DisplayListBuilder.withLayer` で作り直す（span = 出力の項目数。U10 は断片の組み立てで解決）。
- 範囲 `dl*`・描画順 `renderedBoxes`・窓の外 `culledBoxes`・スクロールバーの箱 `scrollBoxes` は、展開（`FragSeq.copyTo(.., OwnerSink)`）で旧経路の `executeTasks` と同じ内容を書く。

### 14.2 見つかった旧経路の暗黙の状態（M1 の実例）

差分テストが並走で 1 件の食い違いを見つけた: **子の親相対の原点は、親の `paintCulled`（描いたか）を読んで決まる**（`PaintOrder.effectiveParentNodeBox`）。旧経路は「分類を全部終えてから、親 → 子の順に実行して、親の実行のたびに印を書く」ので、子を描くときは親の今回の値が入っている。断片の経路は箱を再帰して描くので、印を展開（全箱の描画の後）で書くと、子の描画時には前フレームの値が残り、親が前回省かれていた箱の子が原点 0（絶対座標）で作られた。**親を描く直前に印を書く**ことで解決。これは「描画の入力が、別の箱が書いた状態（`LayoutBox` の印）に依る」暗黙の依存で、F2 で `effectiveParentNodeBox` に親を明示で渡す形（M1）へ直す対象。

## 15. F2: 断片の記憶（子へ降りるのを飛ばす）の実験（2026-11-21。**効果が示せず撤回・旧経路は残す**）

§14.6 の F2 の第一歩として、`FragmentPaint` に箱ごとの記憶（鍵が同じで部分木に新しい印が無ければ、子へ降りず前回の断片を返す）を入れて、全面の描画が旧経路（部分木の保持＋省略＋箱ごとの記憶）と同等以上になるかを測った。**ならなかった**ので、ユーザーの条件（効果が出たら旧経路を削除して 1 本化）を満たさず、実験を撤回した。旧経路は残している。

### 15.1 試したこと

- 記憶の鍵: 親・位置・大きさ・クリップ（実体）・親 id・動く祖先・親相対の原点・子の並び（箱の同一性）・スクロール量・描画の枠組み（省略の有無・窓・大きさ）・「自分と子孫の `paintStamp` の最大値」≤ 作った時の通し番号。
- 部分木の変更印: `LayoutBox` に `subtreeStamp`（`touchPaint` が祖先へ伝える。CAS）と、子の増減（`addChild`・`clearChildren`・`BoxTreeBuilder` の増分の挿入・削除）での祖先への伝播。副作用の再登録（スクロールの節・窓の外の箱・`BoxMemo` の世代）と、絶対配置の箱が外側の包含ブロックのクリップに依ることの印付け（その箱を含む断片は記憶しない）。
- 正しさは保てた: 並走の差分テスト・等価テスト・`ScrollTranslateTest`・`WindowedDisplayListTest`・`ViewportCullingTest`・`IncrementalVsFullTest` は全て緑。

### 15.2 測定（null バックエンド）

| 項目 | 旧経路 | 断片（記憶なし） | 断片＋記憶 |
| :-- | --: | --: | --: |
| showcase `child` display-list | `0.154 ms` | `0.183 ms` | `0.141〜0.219 ms`（構造の伝播を正しく入れると `0.219`） |
| showcase `resizeexact` display-list | `0.328 ms` | `0.421 ms` | `0.473 ms` |
| large-2000 `child` フレーム全体 | `0.74 ms` | `0.74 ms` | `0.75 ms`（パッチ経由のため変わらない） |
| large-2000 `child` の `layout.place` | `0.270 ms` | — | **`0.450 ms`**（全箱の `touchPaint` が祖先へ伝わる費用。伝播を「前回の描画のあとに印がある祖先で止める」にして `0.253 ms` へ戻した） |

- JFR（`resizeexact`・断片の経路）: `FragmentPaint.build` が 62%、うち箱ごとの描画（`drawBoxSelfMemo` → `BoxMemo.appendNodePatched`・`match`）が **50%**。これは旧経路も同じ処理で、断片の経路に固有の費用ではない。旧経路が速いのは、部分木の保持（チャンク）と省略（prune）が箱の描画自体を飛ばしているから。
- 断片の経路の固有の費用（箱ごとの配列・`Fragment`・層の列・記憶の登録の確保）は約 10% で、全面で作り直す描画（`resizeexact` は全箱の印が進む）では記憶が当たらず純粋な負担になる。

### 15.3 結論と次の候補

- **記憶を足しても、全面の描画で旧経路を上回れない。** 旧経路の部分木の保持・省略と同じ程度の「子の描画を飛ばす」条件（変更印・位置・クリップが同じ）を持ち込むだけでは、断片の木の利得（兄弟の多い親の 1 子の差し替えが O(道)）は出ない。利得が出るのは「兄弟 2,000 の親で 1 つの子だけが変わる」場面で、その場面は旧経路ではスタイル変更・子の増減のパッチが担っている。
- したがって旧経路を消して 1 本化するには、**記憶の当たりではなく、変わった箱から根への道を直接組み直す形（`Fragment.withOwn` の本実装）で、パッチと同等以上**になることを示す必要がある。F1b の計測では更新単体が `0.0009 ms`（兄弟 2,000）だった。次の段は次のとおり。
  1. 変更の伝播を、`LayoutBox` の全箱の印でなく**描画側の記憶の親子の鎖**で持つ（`touchPaint` を触らない。F2 の実験で `layout.place` が `+67%` になった原因）。記憶の箱 → 断片の表を 1 回引き、鎖をたどって道だけを組み直す。
  2. スタイル変更（`patchBoxes`）を、その道の差し替えへ置き換えて、`hover`/`style`/`text` が `±10%` 以内であることを示す（現状は `0.001〜0.014 ms`）。
  3. 子の増減（`ChildSlicePatch`）を、親の断片の子の並び（永続ベクタ）の差し替えへ。
  4. 上の 3 つがパッチと同等になった時点で、パッチ・チャンク・prune・`executeTasks`・旧経路を削除する。

## 17. 方針の訂正: パッチの代替を作らない（2026-11-21）

§16 の `FragmentPatch` は**撤回した**（コードも削除）。理由: C1・C2 の目的は「パッチ（前回の出力をその場で書き換え、範囲・順序の数え違いが不具合の源になる経路）をやめて、メモ化（全面と同じ関数を走らせ、変わっていない部分だけ記憶から引く）へ移行し、経路を 1 本にして保守とバグを改善する」ことで、`FragmentPatch` は**同じ種類のパッチを別の形で作り直し、経路を増やしただけ**だった（旧パッチ・断片のパッチ・旧全面・断片の全面の 4 経路）。性能が旧と同等でも目的に逆行する。

### 17.1 守る原則（以後の判断基準）

1. **パッチを新設しない。** 変更の反映は「全面と同じ関数＋記憶」だけ。変わった箱の範囲を書き換える・範囲や順序を数える・後ろの箱の位置をずらす、を行うコードは足さない。
2. **経路は最終的に 1 本。** 断片の経路（`FragmentPaint`）は、旧経路を置き換えるためのもので、併存は移行の間だけ。旧経路・各パッチ・チャンク・prune・`executeTasks` を、断片の経路が同等になった時点で**削除**する（スイッチで残さない）。
3. **性能の差は、保守性のための許容として扱う。** 「パッチが `0.001 ms`」を守るために経路を増やさない。許容する悪化の上限をユーザーと決めて、その範囲でメモ化を作る（現状の目安: showcase `hover` の表示リスト `0.014 ms`・large-2000 `hover` `0.001 ms` は、メモ化では兄弟の走査ぶん数 µs〜数十 µs 悪化する）。

### 17.2 メモ化への道（パッチを経由しない）

§15 の実験（`FragmentPaint` に記憶を入れる）が「効果が示せない」とされたのは、旧経路（チャンク＋prune）と**同じ時間**を目標にしたため。目標を「旧パッチと同じ」でなく「全面の組み立てが記憶で小さくなる」に置き直す。残る費用の見積もりと、必要な部品:

| 部品 | 内容 | 課題 |
| :-- | :-- | :-- |
| 記憶の鍵 | §15.1 の鍵（親・位置・クリップ・親 id・動く祖先・親相対の原点・子の並び・スクロール量・描画の枠組み・部分木の印） | 部分木の印を `LayoutBox` で伝播させると layout が `+67%`（§6-145）。「前回の描画以降に印がある祖先で止める」で `+5%` に抑えられたが、`LayoutBox` のメソッド・行数のラチェットが増える |
| 変更の入力 | 呼び出し側（`UiView`）が持つ「変わった箱」の一覧を、記憶の無効化の入力として渡す案（祖先の鎖を印付け。`LayoutBox` を触らない）。一覧の漏れは `VERIFY` モードとファズが見つける | 入力の漏れ = 記憶の鍵の漏れと同じ種類の不具合。検証モードで機械的に見える |
| 全面の組み立て | 兄弟の多い親では子の走査（記憶の確認 O(兄弟数)）が残る。2,000 兄弟で数十 µs | 許容するか、子の確認を「親の記憶が持つ変わった子の一覧」で飛ばす |
| 消費者 | 平らな `List` と `dl*` を読む消費者のまま。`dl*` は全面の展開で毎回書く（パッチが無ければ数え違いは起きない） | 子の増減のパッチ（`ChildSlicePatch` 等）・スタイル変更のパッチ・`StackingSubtreePatch` は**全て削除**する。それらを使う `UiView`・`LocalPatches` の分岐も削除 |

### 17.3 次の段（パッチの削除を含む）

1. 記憶の鍵と無効化の入力を決め（ユーザーと許容の上限を確認）、`FragmentPaint` に記憶を入れる。`VERIFY_FRAGMENT_MEMO`（記憶が当たったら作り直して比べる）を `:core:test` 常時有効にする。
2. 全面の描画が記憶つきで旧経路（パッチ込み）の許容内になったら、**パッチを全て削除**（`patchBoxes`・`preparePatchBoxes`・`patchSortedSlices`・`StackingSubtreePatch`・`ChildSlicePatch`・`ChildPatchInsertion`・`LocalPatches` のパッチ分岐・パッチ系スイッチ）。
3. 旧全面（`paintTasks`・`executeTasks`・チャンク・prune・`PaintNode`）を削除し、`Shortcut.FRAGMENT_BUILD` を外して 1 本にする。

### 18.6 `StickyScrollNodeTest` の原因と対処（2026-11-21）

## 19. 断片の記憶（C1 の完了。2026-11-21）

1 本の経路（`FragmentPaint`）の上に、パッチでなく**メモ化**で増分を実現した。全面と同じ関数を走らせ、変わっていない部分木だけを記憶から引く。

### 19.1 構成

- **箱ごとの記憶**（既存の `BoxMemo`）: 箱 1 つの項目。変わっていない箱は描画を飛ばす。
- **部分木の断片の記憶**（`FragmentPaint.Memo`）: 箱とその子孫の断片。鍵が全部同じなら子へ降りずに返す。
  - 鍵: 親・位置・大きさ・クリップ（実体）・親 id・動く祖先・親相対の原点・子の並び（箱の同一性）・スクロール量・自分と祖先のスタイルの印・**部分木の印**（自分と子孫の `paintStamp` の最大値）・描画の枠組み（省略・窓・平行移動の方式・ビューポート。窓がずれている間は記憶を使わない）。
  - **部分木の印**: `LayoutBox.touchPaint` が祖先へ伝える。前回の描画（`noteRendered`）以降にすでに印がある祖先で止めるので、1 フレームに何千の箱が触られても伝播はほぼ O(1)（全箱の伝播は layout `+67%`、この方式は `+5%`）。子の増減（`addChild`・`clearChildren`・`BoxTreeBuilder` の挿入・削除）は `touchSubtree` で祖先へ伝える（自分の `paintStamp` は進めない）。
  - **副作用の再登録**: 記憶が当たると組み立ての副作用が起きないので、持ち主の数・スクロールの節・窓の外の箱・箱の記憶の世代を記憶から再現する。
  - **記憶しない断片**: 絶対配置の箱は外側の包含ブロックの中身のクリップに依るので、その間の箱の断片は記憶しない。
- **子の確認を O(1)**: 親の文脈が前回と同じ（親の記憶が `sameContext`）なら子の文脈も同じなので、子はクリップ・位置・大きさ・親 id・動く祖先・スクロール量・部分木の印だけを見る。子の記憶は親の記憶の配列（`kidMemos`）から引く（ハッシュ引きなし。別の箱の記憶でないかを確かめる）。
- **親の組み立てを増分に**（`Fragment.aggregateFrom`）: 子の断片が前回と同じ実体の位置が大半なら、層の列は前回の永続ベクタから、変わった子だけ `set` で差し替える。変わった子が多い・子が少ないときは全面の組み立てと同じ。結果は常に同じ。

| 原因 | 対処 | 効果 |

## 20. 再利用の仕組みの統合と、無効化の鍵（C1m。2026-11-22）

### 20.1 統合したもの

箱ごとの記憶（`BoxMemo`）を削除し、箱自身の項目の再利用を断片の記憶（`FragmentPaint.Memo`）へ移した。
文脈（位置・大きさ・クリップ・親 id・動く祖先・親相対の原点・属性の版・自分と祖先のスタイルの印・子の並び）が前回と同じなら、
部分木の中だけが変わっていても、箱自身の項目（`Fragment.own`）は前回のものを使う。箱の外の入力（中身の大きさ・先頭の断片の位置・
キャンバス背景か・対話規則・文字の影の抑制・placeholder）は `ownReusable` が見る。

### 20.2 無効化の鍵（どの記憶を、何で守るか）

| 鍵 | 持ち主 | 守る記憶 |
| :-- | :-- | :-- |
| `paintStamp`・`styleStamp`（箱ごとの通し番号） | `LayoutBox` | 箱自身（と祖先のスタイル）が変わったか。`pathPaintStamp` |
| `subtreeStamp` | `LayoutBox` | 部分木のどこかが変わったか。`touchPaint`／`touchSubtree` が祖先へ伝える |
| `buildEpoch`・`buildSerial` | `DisplayListBuilder` | 描画の通し番号。記憶が「この番号以前の変更は反映済み」と言うための基準 |
| `attrVersion` | `HtmlNode` | 属性の変更〔印に出ない〕 |
| `memoFrameKey` | `DisplayListBuilder` | 描画の枠組み〔省略・窓・親相対・ビューポート〕。変わると断片の記憶を全て捨てる |
| `paintEpoch`（項目のセルの時計）・`itemVersion`・`contentToken`・`chunkEpoch` | 項目の列・描画側の索引 | 項目の塗りの書き込み・索引の差し替え。**描画側**の再生・損傷範囲・索引の引き継ぎだけが読む |

組み立ての側（箱 → 断片）の鍵は上の上 5 行だけで、描画側（項目 → バックエンド）の鍵は最後の行にまとめた。
両者の境は `ItemDiff` の述語〔同一性＋塗りの時計〕。

### 20.3 結果

- `DisplayListBuilder` `1,581 → 958` 行・`BoxMemo` 791 行を削除。「前回と同じか」の答え方は 5 種類から 3 種類〔断片の記憶・索引の引き継ぎ・再生の鍵〕へ。
- 平行移動の再利用の近似に由来した不具合〔ファズ `nested/21779068`〕が消えた。
- 代償: 子の増減で動く後続の兄弟を作り直す〔`child` `1.65 → 2.14 ms`〕・リサイズで記憶を全て捨てる。どちらも C4〔親相対の不変の配置〕で戻す。
