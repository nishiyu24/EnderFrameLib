## 0. 要約

- 増分の経路は C1・C2 で 1 本になった。しかし**「いつ再利用してよいか」を決める言語が段ごとに別**で、配置の記憶だけが手書きの純粋性フラグだった。C9a〜c で状態を 5 つ足し、そのたびに別の欠陥と費用が出た（§1.3）。
- 構造の答えは 1 つ: **全ての段が、同じ「読み取り集合の鍵」で再利用を決める**。測定の記憶は C3 で既にこの方式で、配置・描画・スタイルをそこへ寄せる。再利用の判定は「記録した読み取りの値が今も同じか」の 1 関数だけになり、フラグは要らない。
- 同時に、**ループを断つ 6 つの原則**（§2）を機械的に固定する: 独立のオラクル（無効化漏れも検出）・計器を 1 か所でゼロコスト・コアは実時計を読まない・状態の予算のラチェット・バグは生成テストとして台帳へ・時間の主張は同時の A/B だけ。
- **全面書き換えはしない**（§9）。K0（足場）だけでも単独で価値があり、K2（配置の移行）は先にスパイクで合否を見る。合否線に届かなければ撤退条件（§5）で止める。

### 1.2 ループの原因（4 つ）

1. **再利用の言語が複数**。構造フラグは「ある構造があれば保持しない」という保守的な述語の集まりで、**新しい場合ごとに足す**。述語は暗黙の前提（「保持されたなら、その下は何も変わっていない」）に依存し、前提が破れると古い結果が残る。
2. **検証が「保持が起きた所」だけ**。保持の誤りは見つかるが、**無効化の漏れ（レイアウトが走るべきなのに走らなかった）は原理的に見つからない**。しかも部分木を単独で置き直すと、断片の管理を祖先が受け持つため偽陽性が出る（§6-177）。
3. **診断・計器が各所に散らばる**。1 箱ごとの `LongAdder` は 2,000 箱の文書で `hover` を約 8% 遅くした（§6-180）。
4. **コアが実時計に依存する**。リサイズの間引きが壁時計で、テストが並列実行でだけ時々落ちた（§6-178）。

## 3. 目標アーキテクチャ

### 3.1 読み取りの台帳（`ReadKind`）

読み取りの種別ごとに: 読む元（箱の幾何・スクロール・ビューポート・スタイルのプロパティ・float 空間・アンカー…）・現在値の取り方・**スコープの解決規則**（読む元が部分木の内側なら外への依存にしない）を 1 か所に登録する。測定の `READ_*`（9 種）・`PARENT_READ_*`（9 種）をそのまま取り込み、配置の種別（原点・親の外寸・自分のスクロール・子孫のスクロール・包含ブロックの幾何・ビューポート・アンカー・float・sticky）を足す。**種別は 20 台。ビット集合で持てる。**

### 3.2 鍵と再利用

```
Key(stage, box) = { readMask, snapshot[readMask の各ビット] }
canReuse(key)   = for each bit in readMask: current(bit) == snapshot(bit)
```

- 版ではなく**値のスナップショット**で比べる（C3 の `MeasureKey` と同じ）。再計算の結果が前回と値として同じなら、依存先から見て変化なし（早期打ち切り）。
- 部分木ごとの再利用は、部分木の**外向きの読み取り**だけを集約する。`cbUp`（包含ブロックが何段上か）は、この「読む元が内側なら外向きにしない」規則の 1 例にすぎない。`F_PURE`・`F_KEPT_PURE`・`F_SCROLL_DEP`・`F_REL_INSET`・`levelNoCb` は鍵に吸収される。

### 3.3 スタイルの読み取り（未決。§8）

「このプロパティの変更はレイアウトに効くか」を、手書きの帯〔`hasLayoutAffectingDiffFrom`〕ではなく、**レイアウトの問い合わせが実際に読んだプロパティ**から導く。`findContainingBlock` が `transform` を読むなら、その読み取りが記録され、`transform` の有無が変わった箱の依存先が自動で再計算される（C9b で特例を足した欠陥が構造として消える）。費用が未決。

### 3.5 オラクル（K3）

テストの間だけ、フラッシュのたびに**独立の面**で最初から作り、箱の木（位置・大きさ・静的位置・スクロール範囲・断片を含む全体）と表示項目を比べる。部分木ではなく全体を別に作るので、断片の管理の人工物は出ない。**実装（K0）**: `FrameOracle`〔テスト側。DOM を `cloneNode(true)` で構造のまま複製し `installDocument` で新しい面へ入れる。HTML に書き出して読み直すとパーサが不正な入れ子を直して偽陽性になる〕。比べるのは箱の木〔種類・位置・大きさ・子の数。スクロール範囲は任意〕で、表示項目は比べない〔途中の色・半径が時間で動く〕。**使える場面は時間と対話の履歴に依らない場面だけ**〔`transition`・`animation`・ホバー・スクロール量・`display:none` の部分木は対象外〕。既存の `MutationFuzz`・`RealDocumentFramesTest` はオラクルの一種で、それを**全ての `StandaloneView` を使うテストの共通機構**にする（既定オフ・`-Pverify.oracle`。ファズと実文書は常時オン）。保持ごとの検証クラス 4 つは、鍵の生成側の**汎用の照合**（ヒットしたら再計算して比べる）とオラクルに置き換える（K6）。

### 3.6 変更台帳と段の状態機械（K5b〔改〕。2026-11-24 追加）

**診断（事実）**: 変更の入口が段ごとに別の物で、再利用の判定が段ごとに別の言語になっている。

| 入口・状態 | 持ち主 | 何を表すか |
| :-- | :-- | :-- |
| `pendingTextNodes`・`pendingChildParents`・`pendingAttrNodes` | `UiView`・`LocalPatches` | 文字・子の増減・描画だけの属性が変わった節の集合（パッチの入力） |
| `StateFlags` の `DIRTY_STYLE`・`DIRTY_SUBTREE`・`DIRTY_BELOW` | `InteractionState` | 再スタイルが要る節・部分木・「下に汚れがある」祖先の印（`DIRTY_BELOW` は祖先へ**伝播するフラグ**） |
| `InvalidationLevel`（7 値）・`repositionPending`・`nonScrollRepositionPending` | `UiView` | どの経路へ流すかの水準（入口の種類から派生する値のはず） |
| `domStructureVersion`・`lastBuiltStructureVersion` | `InteractionState` | 文書全体の構造の版（幅だけの変更で再構築を省く判定にだけ使う） |

結果: ①文字・子の増減・属性ごとに専用の経路〔`LocalPatches`〕と成立条件が要る。②全再計算は、変わっていない箱も 2 つの段〔`RenderTreeBuilder`・`BoxTreeBuilder`〕で 1 回ずつ辿る〔`large-list child` を通常経路に落とすと確保 `317 KB`/f・時間 `+43%`。定数倍の除去後でも `+43%`。計画書 §6-198〕。③「部分木の下に変更が無い」を段ごとに別の仕組みで持つ〔スタイルは `DIRTY_BELOW`、描画は `PaintStamps`、測定は `MeasureMemo`〕。

**却下した案（私の最初の案）**: 子の増減が起きた親・文字の節を、祖先まで印にした集合を `layoutDocument` へ渡し、集合に無い部分木を飛ばす。→ `pendingChildParents` と同種の状態をもう 1 つ足すだけで、`CHILD_PATCH` の成立条件を鍵として共有するのは**パッチの別名**。K1〔再利用の言語は 1 つ〕・状態の予算に反する。

**設計**:

1. **変更台帳 `ChangeLedger`（1 本）**: DOM の変更を**追記するだけ**の列。要素は `(節, 種別, 世代)`。種別は `STYLE_INPUT`〔class・style・属性・対話状態・疑似クラス〕・`TEXT`・`CHILDREN`〔子の増減〕・`PAINT_ATTR`〔描画だけの属性〕・`ENV`〔ビューポート・メディア〕・`SCROLL`。世代は 1 フレームごとに増える整数（`Clock` に依らない）。追記は同期した O(1)。**箱にも節にも新しい欄を足さない**。フレームの始めに台帳を**凍結**〔入れ替え〕し、その世代の変更を各段が読む。
2. **問い合わせは台帳だけに聞く**: 各段は「この節の部分木の下に、前回この段が走った世代より新しい変更があるか」を `ledger.touches(節)` で聞く。実装は、凍結した台帳の節から祖先を辿った集合を**フレームごとに 1 回だけ**作る〔`O(変更数 × 深さ)`。フレームが終われば捨てる。節ごとの `DIRTY_BELOW` のような**持ち越すフラグではない**〕。変更が少ないフレーム〔通常〕は集合が小さい。大量の変更〔`markAllDirty`・`ENV`〕は「全て触れた」とする。
3. **段の状態機械（1 本）**: フレームは `COLLECT`〔台帳を凍結・世代を進める〕→ `STYLE` → `BOX_TREE` → `MEASURE` → `PLACE` → `PAINT` の順に進む。各段は次の 1 つの規則だけで再利用する: **「部分木が台帳に触れられていない かつ 段の鍵〔§3.2〕が同じなら、前回の結果をそのまま返す。辿らない」**。段ごとのスイッチ・パッチ・個別の集合を持たない。水準 `InvalidationLevel` は、台帳の種別の集合から**導く値**になる〔`TEXT` だけ → 文字の箱の測り直し、など〕。
4. **消えるもの**: `pendingTextNodes`・`pendingChildParents`・`pendingAttrNodes`・`InvalidationLevel` の入口側の切り分け・`repositionPending` 系・`LocalPatches` と `CHILD_PATCH`・`domStructureVersion`・`StateFlags` の汚れ 3 ビット〔最後〕。**状態の予算は増やさない**: 各段の移行は、足した欄と同数以上を消す〔`IncrementalStateRatchetTest`〕。
5. **`CHILD_PATCH` が要らなくなる理由**: 子の増減は「親への `CHILDREN` の追記」で、`BOX_TREE` はその親の子リストだけを組み直す〔他の部分木は台帳に触れられていないので辿らない〕。パッチの成立条件〔≤ 4 親・≤ 16 変更・`canPatchChildren` の形〕は要らない。条件が成り立たない形〔表・疑似要素・`display: contents`〕は、その親が**触れられた部分木として普通に組み直される**だけで、別経路へ「退く」判断が無い。
6. **段ごとの副作用の扱い〔未決を含む。§8-6〜8〕**: CSS カウンタは文書順の流れ込みがあるので、**シートがカウンタを使う文書では `BOX_TREE` の飛ばしをしない**〔文書の事実であって箱のフラグではない。現行の `CHILD_PATCH` も同じ除外〕。疑似要素・`display: contents` は部分木の内側で完結する。`nextReusable`〔次フレーム用の再利用表〕は、飛ばした部分木の箱も含める必要がある → 部分更新のとき前回の表を**そのまま引き継ぐ**〔登録し直さない〕形を検討する。

**オラクル（K3）で守る**: ①`-Dverify.oracle=true` で、台帳を使った飛ばしが最初から作った結果と一致する〔既存の `FrameOracle`〕。②**台帳の取りこぼしの変異**〔変更を台帳へ追記せずに DOM だけ変える。`FrameOracleTest` の「通知なしの変異」と同じ作り〕を殺す。③台帳が空でない種別の組合せ〔文字＋子の増減＋属性＋位置の指定〕の乱数列で、通常の全再計算と一致する。

**段取り〔各段は単独で出せる・計測で守る〕**:

## 4. KPI の再定義と測り方

KPI を「構造」「定数倍」「仕組みの費用」「状態の予算」の 4 つに分け、混ぜない。

| 量 | 定義 | 合否線 | 測り方 |
| :-- | :-- | :-- | :-- |
| **増幅率**（構造） | 1 フレームの再計算数 ÷ 変更元の数（段ごと） | 全段・全シナリオ `≤ 10`（確定済み。計画書 §3） | `costGate` の `memo*`（個数・決定的） |
| **1 再計算あたりの費用**（定数倍） | 再計算 1 件の確保量と時間 | 確保＝現状以下。時間＝旧経路水準（display-list `0.43 µs`/項目） | `costGate` の確保量・A/B の時間 |
| **仕組みの費用** | 再利用の判定・計器・検証の費用（再計算しない場合の 1 箱あたり） | 計器オフ `≤ +1%`・鍵の判定 `≤ +3%`（旧版との A/B） | 旧版との**交互 A/B**（下） |
| **状態の予算** | 箱ごとの記憶のフラグ・付帯欄・検証クラス・近道スイッチの数 | **増やさず、K 系の完了で減る**（K2 でフラグ 6＋4 → 鍵 1） | ラチェット（K1 の機械的固定） |

**時間の測り方（固定）**: セッションをまたぐと絶対値が `±40%` ずれる（§6-180）。時間の主張は、**旧版の worktree と現在を交互に 3 回ずつ、中央値**だけで行う。`scripts/ab-gate.ps1`（K0 で作成済み）を、夜間 CI と、時間に効く変更の完了条件に置く。1 回ずつの測定の `±10〜15%` は判断に使わない。

## 8. 未決の論点（K0・K1 の間に解く）

1. **スナップショットの種別ごとの費用（K2 で解決済み）**: 深さの相対値 `cbUp` ではなく、`LayoutReads` の配置参照スタックから部分木外に出る参照（包含ブロック・アンカー・sticky）だけを `PlacementDeps` の配列へ保持・一致時再利用する方式で解決した。
2. **スタイルの読み取り（§3.3）**: プロパティ単位の記録は費用が高いかもしれない。まず「レイアウトが読むプロパティの集合」を段ごとの定数のビット集合として持つ案（読み取りの自動記録ではなく、**台帳に宣言＋テストで照合**。`PaintBoxInputs` と同じ型）を検討する。
3. **インク境界（K4・解決済み）**: 影・outline・変形・絶対配置・overflow の上限を、測定の出力として持てるか → **窓の判定そのものが読む矩形（箱・インラインの断片）だけで足りた**。窓の判定は箱の矩形しか見ない既存の規則で、変形・アニメーションのある箱・レイヤーを持つ箱は窓で省かれず項目を持つ（空の断片に現れない）。位置指定・sticky の子孫は平行移動で動かないので境界を作らず（代理なし）、行に分かれた箱自身も原点の親が箱の外にあるので作らない。境界は窓付きの組み立ての空の部分木に限り、平行移動が起きたとき遅延して作る。窓なしの文書では空の断片が位置に依ることがある〔クリップ等〕ので代理を使わない。
4. **オラクルの費用と作り方**〔K0 で解決: 箱の木の複製で足りた。`layouts` 種 1〜1500 × 45 手で偽陽性 0。履歴のある場面への拡大は K0b〕: 独立の面を作るには DOM の複製（スタイル・対話・スクロールの状態を含む）が要る。小さく作れなければ、箱の木の複製へ縮小する。
5. **並列レイアウト**: 鍵のスナップショットの読み書きがワーカー間で競合しないこと（箱ごとの記憶は箱の持ち主のスレッドだけが書く前提を維持）。
6. **台帳の「触れた節の集合」の作り方（K5b）**: フレームごとに祖先を辿った集合を作る案〔§3.6-2〕で、大量の変更・深い木での費用が許容か。`DocumentArena` の行きがけ番号と部分木の範囲で、集合を作らずに範囲検索で答える案もある〔ただし挿入で番号が連続でなくなる点を要確認〕。K5b の L0 で両方を測って決める。
7. **`nextReusable`（次フレーム用の再利用表）の引き継ぎ（K5b）**: 部分更新で、飛ばした部分木の箱を登録し直さずに済む表の持ち方〔前回の表を引き継ぎ、組み直した部分木の分だけ差し替える〕。登録し直しは O(箱) で、飛ばしの利得を食う。
8. **CSS カウンタ（K5b）**: 文書順の流れ込みがあり、部分木を飛ばすと後続のカウンタ値が変わりうる。当面は「シートがカウンタを使う文書では飛ばさない」〔文書の事実で判定〕。部分木ごとにカウンタの出入りの差分を鍵に持つ案は、使う文書が現れてから。

## 9. 見送った選択肢（検討の記録）

- **全面書き換え（Salsa 型の問い合わせエンジンへ一括移行）**: 設計としては最も綺麗だが、10 万行・全段を一度に変える費用とリスクが大きく、途中で測定・描画の既存の最適化（C1〜C3 の成果）を失う。K1 の台帳と K2 の鍵は、同じ方向へ**段ごとに**進む足場になる。

## 付録 A: 断片の木（C1〜C7 で確定した描画側の設計）

> 旧 `DESIGN_FRAGMENT_TREE.md`（C 系の初期設計書。F0〜F2 の試作・撤回の経緯を含む 826 行）を、**今も効いている設計だけ**に縮めてここへ統合した。試作の数字・撤回した案（`escapees`・`FragmentPatch`・断片の記憶の最初の実験など）は git の履歴と計画書の補足資料を参照。K 系は、ここに書いた描画側の仕組み（断片の記憶・印）を、配置・測定・スタイルと同じ**読み取り集合の鍵**へ寄せる計画である。

### A.1 保守性の拘束条件（M1〜M8）

過去の不具合の出どころは 4 つ: ①手書きの「退く条件」の漏れ ②範囲・添字の数え違い ③出力のその場書き換え ④ビルダーの暗黙の可変状態が鍵に入っていないこと。新しい構造は次で、これらを書き方で不可能にする。

| # | 原則 | 具体 |
| :-- | :-- | :-- |
| M1 | 純粋な組み立て | `build(box, ctx)` は引数と箱の木だけを読む。文脈は不変レコードに集め、鍵はその全欄から機械的に作る |
| M2 | 出力は不変 | `Fragment`・項目は `final` 欄のみ。受け取った側が書き換える口を作らない（`PaintCellRatchetTest`） |
| M3 | 位置を数えない | 表示リストの添字・通し番号を生成側に持ち込まない。順序は子リストの順＋層だけで決まる |
| M4 | 増分専用のコードを持たない | 全面＝記憶が空の増分。挿入位置の探索・後続のずらしは書かない（パッチは全削除済み） |
| M5 | 記憶の鍵は小さな 1 か所 | 鍵の比較・生成と記憶を引く呼び出しを 1 か所に集約 |
| M6 | まず影で動かす | 新しい経路は旧経路と併走して毎回比べ、全部一致してから切り替える（K2 のスパイクの作法） |
| M7 | 最小の構造から | 並びは平衡木でなく、まずブロックの配列（2 段）で足りるかを測る |
| M8 | 部品の大きさと責務を縛る | 1 型 1 責務・1 クラス 400 行以下。`DisplayListBuilder` を太らせない（`FileSizeRatchetTest`） |

検証は 3 層: ①型・単体（参照実装との性質テスト）②差分（記憶あり＝記憶なしの全面。ファズ・実文書）③鍵の漏れ（当たったとき作り直して比べる。鍵の要素を 1 つずつ外すと赤になること）。K0 の `FrameOracle` は②③を「最初から作った独立の面との全体比較」へ一般化したもの。

### A.2 断片・鍵・組み立て

- **断片（`Fragment`）**: 箱 1 つの描画の出力を表す不変の値。箱は親へ **7 つの層の列**（blocks・floats・inlines・負の z・位置指定・正の z・after）を渡し、親は子の列を子の順に並べた永続ベクタで持つ。float・不可分なインライン・位置指定・スタッキングコンテキスト・スクロールバーは、層の種類の違いとして扱う（特別扱いの分岐を持たない。`PaintOrder.classifyPlain`）。
- **スタッキングコンテキスト**: 位置指定・`z-index` 付きの子孫は、属する根で z と文書順に安定整列して合流する。フィルタ・マスク・ブレンドの層の `span` は根の断片の項目数（O(1)）。Top Layer は専用の層（`HOIST`）。窓付き表示で窓の外の箱は空の断片（culled）。
- **組み立て（全面と増分が同じ関数）**: `build(box, ctx)` は、鍵が前回と同じなら子へ降りずに記憶を返し、違えば子を組み立てて親の層を作る。子の増減は子リストの差し替えだけで、親の層は前回の永続ベクタから変わった子だけ差し替える（`Fragment.aggregateFrom`）。
- **鍵（`FragmentPaint.Memo`）**: 親・位置・大きさ・クリップ・親 id・動く祖先・親相対の原点・子の並び（箱の同一性）・スクロール量・自分と祖先のスタイルの印・**部分木の印**（自分と子孫の `paintStamp` の最大値）・描画の枠組み（省略・窓・ビューポート。変わると記憶を全て捨てる）。**親の文脈が前回と同じなら子の文脈も同じ**なので、子の確認は O(1)。記憶が当たると副作用（持ち主の数・スクロールの節・窓の外の箱）が起きないので、記憶から再現する。絶対配置の箱の間の断片は記憶しない。
- **部分木の印**: `LayoutBox.touchPaint` が祖先へ伝える。前回の描画以降にすでに印がある祖先で止めるので、1 フレームに何千の箱が触られても伝播はほぼ O(1)。子の増減は `touchSubtree`。
- **自身の項目の再利用**: 文脈が同じなら部分木の中だけが変わっていても、箱自身の項目（`Fragment.own`）は前回のものを使う。箱の外の入力は `ownReusable` が見る。

### A.3 無効化の鍵（どの記憶を何で守るか）

| 鍵 | 持ち主 | 守る記憶 |
| :-- | :-- | :-- |
| `paintStamp`・`styleStamp` | `LayoutBox` | 箱自身（と祖先のスタイル）が変わったか |
| `subtreeStamp` | `LayoutBox` | 部分木のどこかが変わったか（`touchPaint`／`touchSubtree` が祖先へ伝える） |
| `buildEpoch`・`buildSerial` | `DisplayListBuilder` | 「この番号以前の変更は反映済み」の基準 |
| `attrVersion` | `HtmlNode` | 属性の変更（印に出ない） |
| `memoFrameKey` | `DisplayListBuilder` | 描画の枠組み。変わると断片の記憶を全て捨てる |

組み立ての側（箱 → 断片）の鍵は上の行、描画側（項目 → バックエンド）は項目の同一性だけ（A.4）。**この表が、K 系で「読み取り集合の鍵」へ寄せる描画側の現状**である。

### A.4 描画側: 項目は完全に不変（C6）

- 項目と `PaintCell` の欄は全て `final`。塗りの書き込み・各種の通し番号・ブロックの時計・`contentToken`・`itemVersion` は削除済み。変化の判定は `ItemDiff.unchanged(prev, cur)` ＝ **同一性だけ**。
- 平行移動（スクロール・窓のドラッグ・sticky）は別の表 `PaintOffsets`（要素 ID 鍵・表全体の `version`）。バックエンドは項目を描くとき表を引いて姿勢に足す。位置変化の検出は `DamagePlanner`・`StaticFrameGate` が `version` と前回スナップショットの差分だけで行う。
- 合否線は GPU・CPU・画素の 3 者一致（`CpuScrollBlitPixelTest` ほか）。`PaintCellRatchetTest`・`PaintOffsetsTest` が不変性を守る。

### A.5 経路の予測と検証（C7）

経路は人の書いた分岐でなく 1 つの規則〔記憶の鍵が同じなら再利用〕から決まる。

| 状態 | 条件 | 選ばれる段 |
| :-- | :-- | :-- |
| 全て同じ | 文脈が同じ ∧ 部分木の印が前回以下 | 0: 部分木ごと再利用 |
| 自身だけ同じ | 文脈・箱の外の入力が同じ ∧ 部分木の印が新しい | 1: 自身の項目を再利用、子を組み直す |
| 自身が違う | 上記以外 | 2: 作り直す |

- **印の仮→確定（`PaintStamps`）**: 書き込み口は仮の印を付け、描画の直前に出力の署名と子の並びを前回の確定と比べて、変わったときだけ確定する（early cutoff / backdating）。署名は描画が読む出力の上位集合にする。
- **`PathPredictionTest`**: 箱の入力の前後比較だけから理想の段を予測し、実際の段と突き合わせる。実際 < 予測＝不健全（古い項目）は 0 件、実際 > 予測＝取りこぼしは上限で見張る（残り約 1,100 件は予測がクリップの実体を見ない限界と位置・大きさの伝わり方）。
- **`PaintReadSetTest`**: 箱の欄を 1 つずつ摂動して「描画が読む欄」を実測し、署名の宣言（`PaintStamps.SIGNATURE_FIELDS`・`COVERED_ELSEWHERE`）と照合する。限界: 欄にない依存（祖先のスタイル・クリップの実体・位置の親）は洗い出せない。→ K 系で台帳へ。
- **`BoundedModelCheckTest`**: 小さな文書・12 手・長さ 4 以下の全 22,620 列で、毎手「記憶あり＝記憶なし」を確かめる。ファズが通っていた不具合（属性だけの変更・`::first-line`）を検出した。範囲外: スクロール・時間・ビューポート。
- 先行例との対応: Blink `PaintController`（cached subsequence）＝断片の記憶、Blink の under-invalidation 検査＝`VERIFY_BOX_MEMO`・`OwnItemsVerifier`、Salsa の red-green / early cutoff＝`PaintStamps`、Stylo の `RestyleDamage`＝3 段、React の bailout＝鍵の比較による部分木の再利用。違いは、経路の効率まで見る独立の予測器・読み取りの実測・有界の全列挙を持つこと。予測器は記憶と同じ人が書くので独立性は完全でない。
